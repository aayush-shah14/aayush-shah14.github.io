The problem

A useful assistant in the operating room cannot behave like a conventional chatbot. It has to understand what is happening in the video stream, preserve procedure and patient context, respond quickly to voice, and fail safely when the available evidence is incomplete.

What I worked on

  • The multi-agent runtime and the path from live context to tool calls and responses.
  • A local voice stack with streaming ASR, LLM generation, and TTS.
  • Inference deployment across two edge GPUs, including vLLM, ONNX, Triton, and gRPC streaming.
  • Validation, human-in-the-loop safeguards, and traces for diagnosing context and tool failures.

Latency work

The first useful measurement was not total request time; it was the delay a surgeon actually feels between finishing a question and hearing the first audio. In a local deployment, the main components measured roughly 0.25 seconds for speech recognition, 0.52 seconds for the LLM round trip, and 0.55 seconds for TTS startup, producing 1.31 seconds end to end.

Prefix caching, streaming generation, and starting audio before the response was complete mattered more than optimizing a single isolated model call.

What changed

The system supported twelve arthroscopic workflows and reached 95% task success across twenty dry-lab sessions. The work also made failures easier to inspect: a bad answer could be traced back to context selection, perception, tool execution, or generation rather than appearing as one opaque model error.
